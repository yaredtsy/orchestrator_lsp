## 1. How the core learns what drivers exist

Today the extension passes one path (`driverPath`) and the core assumes Python. For several drivers the core must know, **before starting any of
them**, which files each one handles. Starting every driver just to ask would cost start-up time and memory for languages the project does not use.

So each driver ships with a small **manifest** file next to its program:

```
extension/bin/
├── vnoc                               the core
├── vnoc-driver-python                 a driver
├── vnoc-driver-python.json            its manifest
├── vnoc-driver-go
└── vnoc-driver-go.json
```

```json
{
  "name": "python",
  "version": "0.1.0",
  "protocol": 1,
  "program": "vnoc-driver-python",
  "files": {
    "extensions": ["py", "pyi"],
    "names": []
  },
  "languageIds": ["python"]
}
```

| Field | Used by | For |
|---|---|---|
| `protocol` | core | skip a driver the core cannot talk to, without starting it |
| `program` | core | the file to start, relative to the manifest (`.exe` is added on Windows) |
| `files.extensions` | core | routing: lower-case, without the dot |
| `files.names` | core | whole file names with no useful extension (`Dockerfile`, `Makefile`, `BUILD`) |
| `languageIds` | extension | VS Code's language ids, for the `when` clauses on menus and buttons ([`01`](01-who-does-what.md) §4) |

How it flows:

```
extension   passes ONE thing to the core: the folder  …/bin          (initializationOptions.driversDir)
core        reads every *.json there → a table: extension → driver         (no process started)
            scans the project (§2) → sees which drivers are actually needed
            starts only those, lazily, on the first file sent to them
            handshake: name / protocol must agree with the manifest, else the driver is refused and logged
            answers the extension's initialize with: languageIds of the drivers found
extension   setContext("vnoc.languageIds", [...])
```

The manifest is generated by the driver's own build (one source of truth: the same constant the driver uses to answer `initialize`), so it cannot
drift from the program.

This refines [`06-drivers.md`](../06-drivers.md) §3a and §5, which had the core read `files.extensions` from the handshake. The handshake still carries
it, as a check; the manifest is what makes lazy starting possible.

## 2. Which files are in scope, and which driver gets each one

One pass over the project, in the core:

```
for each entry under the opened folder
├── hidden (name starts with ".")            skip      (.git, .venv, .vnoc …)
├── ignored by .gitignore                    skip
├── outside [index] include / inside exclude skip      (vnoc.toml, optional)
├── a symlink                                skip      (never follow: loops, and paths outside the repo)
├── a folder                                 keep as a folder; read its .vnoc-id if present
└── a file
    ├── name in some manifest's files.names        → that driver
    ├── extension in some manifest's extensions    → that driver
    └── neither                                    → no driver (§4)
```

Then, for a file that has a driver:

| Check | Then |
|---|---|
| larger than the size limit (1 MB to start with **[measure]**) | listed as a file, not outlined: "too large to read" |
| not valid UTF-8 | listed as a file, not outlined |
| the driver fails or times out on it | listed as a file with a problem mark; the rest of the project is unaffected |
| more files than the project limit | stop, and say so (the `truncated` flag that exists today) |

Matching is by **file name only**. The core never opens a file to guess its language (no shebang sniffing, no content detection): it is slow, and a
wrong guess sends a file to a parser that fails on it.

**Two drivers claim the same extension** (`.h` for C and C++): the first manifest in name order wins, and the core logs the conflict once. A project
that needs the other one says so in `vnoc.toml`, when that case really appears:

```toml
[drivers]
h = "cpp"          # reserved, not read in 0.1
```

## 3. "What language is this project?"

You do not need to detect it, and you should not try. Real repositories are mixed (Python + TypeScript + SQL + shell), and "the project language" would
be a guess that is wrong for half of them.

The scan in §2 already gives the true answer, per file. After it the core knows:

```
python       87 files   driver: vnoc-driver-python 0.1.0     started
typescript  120 files   driver: none
go            0 files   driver: vnoc-driver-go 0.1.0         not started (not needed)
(other)     311 files   no driver
```

- A driver is started **because files for it exist**, not because of a setting or a marker file like `pyproject.toml`.
- This table is worth showing. Put it in the output channel at start, and as one muted line under the Structure view:
  `Python · 87 files` or `Python · 87 files — 120 TypeScript files are not shown (no driver)`.

The only place a project file like `pyproject.toml` or `go.mod` matters is `vnoc/environmentInputs` (call trees, [`02`](02-what-a-driver-must-do.md)
§4), and there it is the driver that names it.

## 4. Files that no driver claims

A README, a YAML config, a SQL migration, a language you have no driver for yet. Three questions:

| Question | Answer |
|---|---|
| **Are they in the tree?** | Not by default: the Structure view shows code V-NOC understands. A "Show all files" toggle is open question Q2, after 0.1. Their **folders** are always there if they contain at least one shown file. |
| **Can they have docs?** | Yes. "V-NOC: Add doc" in the Explorer's right-click menu works on any file or folder. The node is found by its path. |
| **Do they get a marker?** | **No, never.** Nothing is written into a file unless a driver planned that edit. `id_in_code = "no"` in `node.toml`. |

What "found by its path" costs: renaming or moving the file makes the node Missing until you Relink it (one click, and the Missing list tells you).
Release 0.4 adds rename listeners, so a rename done inside VS Code is followed automatically.

For a file with a driver that is too large or unreadable, the same applies: docs by path, no marker.

When a driver for that language arrives later, nothing has to be migrated: the node already exists, and "Write ID" on it adds the marker.

## 5. Folders

Folders have no language. The core handles them alone ([`05-identity/04-folders.md`](../05-identity/04-folders.md)): the `.vnoc-id` file is V-NOC's
own, so there is no comment syntax to worry about and no driver involved. A new driver changes nothing here.

One interaction to know: a folder appears in the tree when it contains at least one file in scope with a driver. A folder of only YAML files is not in
the tree, but can still be documented from the Explorer.

## 6. A language with no driver installed, and downloads

In 0.x every driver that exists is inside the VSIX (`bin/`), so "not installed" means "nobody wrote it yet". There is nothing to download and nothing
to choose.

**What 0.1 does:** the muted line from §3. No pop-up, no prompt.

**When downloads make sense** (after 1.0, [`06-drivers.md`](../06-drivers.md) §5): when drivers are big enough or many enough that shipping all of
them to everyone is wasteful, or when other people write drivers. The manifest already carries what that feature needs:

```
later
├── a list of known drivers (name, extensions, download URL per platform, checksum, signature)   fetched or bundled
├── scan finds 120 .ts files and no local driver for "ts", but the list knows one
├── the Structure view offers: "TypeScript support is available. [Install]"                      one click, never automatic
└── download → verify → put under the extension's global storage → the core reads its manifest like any other
```

Rules to hold on to when that day comes: never download without a click, verify before running, and a failed download leaves V-NOC working exactly as
before.

## 7. Edge cases

| Case | 0.1 behaviour |
|---|---|
| A file with two languages in it (`.vue`, `.html` with `<script>`, `.ipynb`, Markdown with code blocks) | one extension → one driver, or none. Embedded languages are not looked into. |
| Generated or vendored code inside the repo | usually ignored by `.gitignore`; otherwise exclude it with `[index] exclude`. A driver must also refuse to write markers into generated files ([`04`](04-markers-and-unsafe-files.md) §3). |
| A file whose extension changes (`.js` → `.ts`) | its path changed, so it is a new file to the index. A def with a marker is found again if the new driver reads the old marker; otherwise Missing → Relink. |
| The same extension with different meanings (`.m`: Objective-C or MATLAB) | first manifest wins; `[drivers]` override when needed |
| A driver is removed or fails to start | its files are listed without an outline; nodes inside them that have docs show as "driver unavailable", **not** as Missing |
| Upper-case extensions (`.PY`) | compared lower-case |

That fifth row matters: Missing must mean "V-NOC looked and it is not there". When V-NOC could not look, it must say that instead, or people will
Remove docs that are fine.
